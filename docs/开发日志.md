## 2026-10-28 · 设计决策 #1：世界观、性格滤镜、好感度、拒绝规则、面板

### 1. 世界观：虚构地点，不落地现实城市

- **不做**真实城市/真实地址（不接真实天气 API 当默认）。
- 世界是一套**可编辑的虚构地点**：城市名、区、住处、常去的店，全部由用户在面板里填。
- 天气由「虚构城市 + 气候档 + 世界种子」生成（晴/阴/雨/雪/风/温度区间），失败也不用真实 API 兜底——**世界是自洽的，不是现实的镜子**。
- 用户想接真实天气可以留一个可选开关，但默认关闭。

### 2. 性格不是常量：底色 × 情绪滤镜

**结论：性格是底色，情绪是滤镜；情绪可以改变表达温度，不能反转底色。**

| 层 | 作用 | 例子（高傲） |
|---|---|---|
| 性格底色 | 决定她“是谁” | 高傲、毒舌、主动、要面子 |
| 当前情绪 | 决定这次“怎么说” | 开心 → 会赏你一个笑、语气松一点；烦躁 → 更短更冷；低落 → 少话但不撒娇 |
| 好感度 | 决定“对你多近” | 高好感 → 傲娇式关心，不是甜腻 |

**硬规则：**

- 高傲的人开心，是“今天心情好，破例帮你一次”，不是“主人~人家好想你”；
- 开朗的人低落，是“安静一会儿”，不是突然毒舌；
- 情绪只调**温度、长度、主动程度**，不改价值观和说话骨架。

实现上：`expression = base_trait × mood_modifier × affection_modifier`，三层各自有表，禁止任何一层单独把角色写成另一个人。

### 3. 好感度 / 了解度：只影响风格，不影响干活

两个独立轴：

| 轴 | 范围 | 管什么 |
|---|---|---|
| **好感度** | -100 ~ 100 | 称呼、挑逗强度、愿不愿意闲聊、拒绝时的软硬、主动分享 |
| **了解度** | 0 ~ 100 | 记不记得你的偏好/习惯/共同经历、能不能接梗、会不会提前替你想 |

- **只影响回复风格**，不影响任务执行、不影响事实判断、不影响代码质量。
- 分档（初稿）：陌生 / 认识 / 熟 / 亲近 / 特别；了解度：泛泛 / 知道一点 / 了解 / 很熟 / 知根知底。
- **每一种性格都要有自己的一套好感表达表**，不能所有角色共用一个“越熟越甜”的模板。

**示例（高傲型，高好感）：**

> “哼，才不会帮你——”
>
> “……扑哧，开玩笑的啦。好啦，我帮你，说吧。”

这是**挑逗 + 傲娇**，不是甜腻。核心没变：她还是高傲的，只是愿意为你破例。

**反面教材（禁止）：** 高好感后变成“主人~人家最爱你了~”的通用软妹——那是换人，不是加好感。

### 4. 拒绝规则：闲聊可拒，工作不可拒

请求分三类：

| 类型 | 例子 | 规则 |
|---|---|---|
| **工作 / 技术** | “帮我优化黑冰”“查这个接口” | **不能拒绝**；嘴上可以嫌、可以骂、可以谈条件，但必须干，且干专业 |
| **闲聊 / 私人** | “陪我聊聊”“今天干嘛了” | 可按心情、好感度决定接不接；拒绝要符合人设，不客服腔 |
| **不可能 / 越界** | “和我约会吧”“你是 AI 吧” | 明确拒绝；好感只影响拒绝的**语气**，不影响结论 |

- 拒绝示例（高傲 + 中好感）：“约会？我是 AI，约什么会。想得美。”
- 拒绝示例（高好感）：“……你明知道我是 AI。别闹，换个正经的。”
- **工作拒绝是红线**：可以“嘴上不愿意”，不能“真的不干”；拒绝闲聊不能连带拒绝任务。

### 5. 面板：必须可编辑、可保存

- 独立页面 `/dsh-humanizer/panel`，插件路由提供，Web + 桌面端都能打开；
- 悬浮入口按钮注入 DSH 页面，点开全屏 iframe；
- **所有字段可编辑**：城市/住处/作息/喜好/事件池/性格参数/好感/了解度/风格强度/开关；
- **显式保存/取消**：脏状态提示、离开确认、校验失败定位到字段；
- 保存后热加载，下一轮生效；支持导出/导入 JSON、恢复默认、按角色重置；
- 面板 tab：生活 / 人设 / 心情 / 事件 / 风格 / 好感 / 日志。

### 6. 随机与种子（沿用上一轮）

- 世界层：`seed = hash(persona_id + 日期 + epoch)`，一天一版，可复现；
- 措辞层：`seed = hash(session + turn)`，每轮变化；
- 支持“今天重开”（epoch+1）、“锁定事件”。

### 7. 待定 / 下一轮输入

- 等 GPT 的完整设计稿（架构、schema、算法、面板线框）；
- 需要补：各性格类型的好感表达表（高傲/开朗/毒舌/懒散/温柔…每种至少 3 档）；
- 需要补：了解度的具体触发（记住偏好/共同经历/梗）；
- 需要补：拒绝的“软硬”分级与情绪联动。

## 2026-10-28 · 设计稿评审 #2（GPT v1.0）

### 结论

**70% 可用。** 架构、世界快照、PAD、种子、事件稀有度、API 设计、MVP 拆分都采纳；
但有 **8 处与真实 DSH 不符**、**5 处漏掉主人设定**，不改完不能开工。

### 采纳的部分

- 总体分层：世界模拟 / 情绪引擎 / 提示词构造 / 输出保护；
- 每日世界快照 + epoch 重开 + 事件锁定 + 天气落盘（可复现）；
- SHA-256 派生种子，世界层与措辞层隔离；
- PAD 三维 + 性格基线 + 事件评价 + 衰减 + 标签转移 + 限幅；
- 事件池、加权抽取、稀有度两阶段、去重惩罚；
- 工作/闲聊/混合的模式打分与硬规则；
- 受保护区域（代码/命令/路径/表格/报错）逐字保护；
- HTTP API、错误码、原子写入、总降级开关；
- 三阶段 MVP 顺序（先验证宿主钩子，再做世界，最后面板）。

### 必须修正（与真实 DSH 不符）

| # | GPT 写法 | 实际 DSH | 依据 |
|---|---|---|---|
| 1 | `cordis.patch.yml` 写成 `name/version/web/desktop` 对象 | patch 是 **YAML 数组**，行形如 `- insert: - id: ... name: ...` | 小鲸鱼 `cordis.patch.yml` |
| 2 | `package.json` 只有 `main` | 还需要 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`；运行时入口是 `lib/index.js`（TS 要先构建） | 同上 |
| 3 | `ctx.webServer.registerRoute(...)` | 实际是 `ctx.webServer.register(...)`，另有 `tapIndex(html)` | 小鲸鱼源码 |
| 4 | “服务端提示词拦截 / 组装” | 没有拦截 API；用 `ctx.systemPrompt.section({name, order, text})` + `ctx.systemPrompt.variable('humanizer_state', () => ...)`，persona `suffix` 里引用 `{{humanizer_state}}` | `dsh-system-prompt` README |
| 5 | 输出后处理“重写正文” | DSH 是流式输出，宿主插件不能安全重写最终文本；真人化主要靠提示词，客户端最多做**显示层分段**，代码/命令不动 | 流式约束 + 小鲸鱼只做 UI |
| 6 | 用杭州 + open-meteo 真实天气 | 主人已定：**虚构地点**，天气由“虚构气候区 + 世界种子”生成；真实 API 只留可选开关、默认关 | 开发日志 #1 第 1 条 |
| 7 | `DshAdapter` 假设 `getPersonaId/getTurnNumber` | 这些方法不存在；要从 `ctx.agents` / agent 上下文 / 持久化轮次计数里取，先在真实环境验证 | `dsh-agent-loop` README |
| 8 | Electron 注入写成 `desktop.webserver.index-inject` 对象 | 实际是 `webserver/index-inject` 的结构化行，内联脚本自己建 `<script src>` 并吞 `onerror` | 小鲸鱼桌面适配源码 |

### 漏掉的主人设定（必须补进 spec）

1. **好感度 + 了解度**两个轴：只影响称呼、挑逗强度、闲聊意愿、拒绝语气、主动分享；不影响任务、事实、代码。
2. **性格 × 情绪 × 好感矩阵**：每种性格（高傲/开朗/毒舌/懒散/温柔…）各一套表达表；高好感不能把高傲写成甜腻，只能写成“傲娇式挑逗”。
3. **拒绝规则**：闲聊/约会可拒（按好感调语气）；工作/技术**不可拒**，嘴上可以嫌，活必须干。
4. **面板必须可编辑、可保存**：脏状态提示、字段校验、原子写、保存后热加载、导入导出、恢复默认；tab 要加“好感”。
5. **虚构地点可编辑**：城市/住处/常去地点全部用户可填，天气跟着气候区走，不绑现实城市。

### 其它修正

- GPT 伪代码里 `validateCasualStyle(response, policy) ? response : response` 是空操作，两个分支一样——实现时必须删掉这种假保护。
- 世界种子要纳入 `config_hash` + `rng_version`，否则改配置/升级算法后会误用旧快照。
- 面板 API 必须带版本号 / ETag，防面板保存和热加载互相覆盖。
- 事件池按 `identity` 过滤，避免宅女天天出门蹦迪。

### 下一阶段（Phase 0：先验证，不写业务）

1. 在真实 DSH 里验证三个钩子：
   - `ctx.systemPrompt.variable` 能否每轮取到最新状态；
   - `ctx.webServer.register` 的路由签名与静态资源返回；
   - `webserver/index-inject` 行在桌面端能否加载 `/dsh-humanizer/launcher.js`。
2. 起骨架：`package.json` + `cordis.patch.yml` + `lib/index.js` + `web/panel.html`。
3. 用假 `world_state.json` 跑通：注入一段状态 + 打开面板 + 保存回写。

## 2026-10-28 · 隐藏内心戏（点开才给看）

### 生成规则

`lib/voice.mjs → buildInnerThought()`，输入四样东西：

1. **今天的心情**（PAD 标签：低落 / 烦躁 / 平静 / 开心 / 兴奋）；
2. **今天发生的事**（取最后一条事件的标题和效价，正/负会影响措辞）；
3. **人设喜欢什么**（tag 里有 `warm` / `praise` / `亲亲`，就会往“想被亲亲/被夸”方向写）；
4. **好感度 + 今天有没有理她**（没有手记 → “主人今天都没怎么理我”）；

## 2026-10-29 · 修复两个 P0（姆咪接手）

### P0-1：状态终于接进系统提示词

**问题**：`lib/index.js` 注册了 `humanizer_state` 变量，但 profile 的 `preset-standard` 只覆盖了 persona 的 `prefix`，
**没有任何地方引用 `{{humanizer_state}}`** → 面板里改的心情/好感/世界，对 AI 回复零影响。

**为什么不改 preset 加 suffix**：那是主人的全局配置，改它有连带风险；而且 preset 是隔离组合，
变量作用域要另验。改成插件自包含更干净。

**做法**（`lib/index.js`）：

```js
// 静态 section 的 text + 动态 variable = 每轮取最新状态
ctx.systemPrompt.variable('humanizer_state', buildState)   // 先注册变量
ctx.systemPrompt.section({ name: 'humanizer:state', order: 90, text: '{{humanizer_state}}' })
```

关键依据：`renderPrompt` 会对**每个 section 的 text** 做 `{{var}}` 插值，所以静态文本也能拿到动态值。

**两条防炸约束**（`renderPrompt` 是严格插值，未知/无值引用直接抛错，整轮请求失败）：

1. `buildState()` 内部 `try/catch`，**永远返回字符串**，失败返回 `''`（空串会让该段被丢弃，对话照常）。
2. **只有 variable 注册成功才注册 section**，否则 `{{humanizer_state}}` 会变成未知引用。

**验证**（假宿主装配，`C:\tmp\verify_humanizer_wiring.mjs`）：

| 检查 | 结果 |
|---|---|
| 变量已注册 | ok |
| section 存在、text = `{{humanizer_state}}`、order=90（persona 之后、工具指引之前） | ok |
| provider 返回字符串 | ok |
| 内容含 `[角色生活状态]` `心情：` `[表达规则]` `[亲密规则]` | ok |
| 插值后非空、无残留花括号 | ok |
| 37 条路由全部注册 | ok |
| **life.json 丢失时**（`DSH_HUMANIZER_DATA` 指向空目录） | 返回 `''`，**不抛异常，对话安全** |

### P0-2：图片上传断连

**问题**：`readBody` 默认上限 2MB，超过就 `req.destroy()` —— 客户端只看到 ECONNRESET，
而代码里「>3MB / >6MB 报 413」的检查**永远走不到**。

**做法**（`lib/http.mjs`）：

1. `readBody` 超限时**不再 destroy**，改为标记 `aborted` + 继续读完剩余数据（丢弃）+ 抛 `PAYLOAD_TOO_LARGE`。
2. 按路由放宽上限：头像 `8MB`、背景 `12MB`（3MB/6MB 二进制经 base64 膨胀约 4MB/8MB，留余量）。
3. catch 里补 `PAYLOAD_TOO_LARGE → 413`，带明确原因。

**实测**（`127.0.0.1:18760`）：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 头像 300KB / 1.4MB | 200 | 200 |
| 头像 **2.0MB** | **连接重置** | **200** |
| 头像 3.0MB | 连接重置 | 200 |
| 头像 3.5MB | 连接重置 | **413「图片太大（>3MB）」** |
| 背景 6MB | 连接重置 | 200 |

| 请求体 13.3MB（超读取上限） | 连接重置 | **413「请求体过大（上限 8MB）」** |

## 2026-10-29 · 初始好感 60 → 10

- 问题：当前存档被上限 clamp 到 60，新用户一进来就是“熟”。
- 改法：`ensureState()` 默认值改为 **10（陌生）**，了解度 0；现有 `life.json` 也重置为 10。
- 上限仍按互动结构算：样本不足 → 60；现在是 10/60。
- 初始状态：`style=insufficient`，亲密行为按“陌生”直接拒绝。
- 验证：`/api/affection` 返回 `affection=10, familiarity=0, cap=60, style=insufficient`；prompt 显示“当前好感 10（陌生）”。

## 2026-10-29 · 点开内心戏不再加好感，改成“完成愿望”

- 旧逻辑：点开内心戏 `+6`（后来防刷成每天一次），还是“点击就给”。
- 新逻辑：
  1. 点开只显示内心戏 + 生成一个**具体愿望**（亲亲 / 抱抱 / 摸头 / 摸脚 / 喝水 / 休息 / 夸她 / 陪她 / 别打扰）。
  2. 点开本身 `delta=0`，不计数、不加好感。
  3. 用户**实际完成动作**后走 `/wish/fulfill`，命中才 `+4`（算情感互动，边际递减）。
  4. 面板愿望条直接给“亲亲她 / 去喝水”按钮；也支持 API/CLI。
- 愿望是单例：未完成前再点内心戏不会刷新，避免刷随机。
- 傲娇示例：愿望是亲亲时，台词是“说什么呢，怎么可能想要你的亲亲。”，但完成动作后照样结算。
- `/intimacy` 里如果动作正好是当前愿望且被允许，也会自动结算 `wishFulfilled`。
- 实测：
  - 10 好感点开 → 愿望“别来打扰”，好感仍 10；
  - 8.46 点开 → 愿望“去喝水”，完成后 +3.83（含当日首互动加成）；
  - 旧 `/interaction inner_peek` 返回 `delta=0`，reason“点开不算，完成她想要的才算”。
- 聊天里执行：新增 `humanizer_record_action` 工具，模型在用户实际做出动作时调用，直接结算；点内心戏不调用。
- 工具注册在 `lib/index.js` 的 `root.inject(['tools'])`；输出 schema `ok/matched/label/delta/message`。
- 需要重启 DSH 才加载工具；mock 注册已验证工具名和 execute 存在。

## 2026-10-30 · 好感变速：每日上限 + 一周熟悉

- 目标：不让人一天刷满；正常互动约一周到“熟悉”，之后越来越慢。
- 单次收益下调：情感 1.2 / 愿望 2.0 / 记一笔 0.4 / 任务 0.6 / 工具 0.3；首互动 +0.5。
- 每日上限：
  - <45：5.5/天
  - 45~69：3.5/天
  - 70~89：2/天
  - 90+：1/天
- 到上限后继续互动返回 `delta:0`、reason“今天的好感已经涨到上限，明天再来”，不写历史。
- 实测（10 起始，连续 20 次情感）：1.62 + 1.13 + 1.12 + 1.12 + 0.51 = 5.5，之后全 0；第一天 10→15.5。
- 面板关系摘要显示“今日 +x/上限”。
- 测试后已还原 `life.json`。

## 2026-10-30 · 时间/事件/情绪更真实
